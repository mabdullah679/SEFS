SEFS - SHARED EFS FOR A PYTHON WRITER AND A SPRING BOOT READER (plain twin of README.md, 2026-10-25)

WHAT IT IS
One command builds, in your own AWS account: a private network across two data centres, one encrypted shared file system, a Python app that writes files to it and a Spring Boot app that reads the same files but cannot write, daily backups kept 35 days, a rule that moves untouched files to cheaper storage after 30 days, alarms and a dashboard, a read-only checking role, a password-protected 2.5D map of everything that is running, and the plumbing that lets every later change deploy itself when you push to GitHub with the word "check".
It implements the spec "Shared EFS for Multi-App.docx". The 15 requirements are numbered R1 to R15 in PLAN.md. If an AI agent is helping you, point it at AGENTS.md first.

WHAT YOU NEED
An AWS account you can administer and a login for it. An empty GitHub repository you own, because the automation's deploy role trusts exactly one repository and its main branch. On your machine: Terraform 1.9 or newer, Docker, the AWS command line (version 2), jq, make and bash (Windows: use WSL2). You don't need Java, Maven, Python or Node; the apps and the map's web page build inside Docker. Your upload link should manage about 250 KB/s or better for a first deploy from a laptop (about 290 MB of images); at 15 KB/s (measured 2026-10-27) every upload attempt times out, so on a slow link deploy from GitHub instead (push with "check full" and approve the run); deploys from GitHub don't have that problem.

HOW TO RUN
Run this single command and enter inputs where requested: ./sefs setup (after signing in to AWS in your shell). ./sefs help lists every other verb; ./sefs show <keyword> prints any deployed ID (efs, subnet, cluster, log, backup...), ./sefs status shows services, file system and alarms, ./sefs logs writer or reader shows the newest app log. The numbered steps say the same thing in full.
1. Create an empty repository on GitHub, clone this one, point it at yours, and push.
2. Sign in to AWS in your shell.
3. Run ./sefs setup (the same as ./setup.sh). It checks your tools, shows which AWS account you're signed in to and asks you to confirm, asks for the region, an alarm e-mail (optional), the e-mail for the map login (blank means the alarm e-mail; AWS mails that address a temporary password) and your GitHub repository, writes a local settings file that never leaves your machine, creates the shared state storage and the deploy role once, asks for any secrets the project lists (none today) and stores them only in AWS's parameter store, then deploys everything (about 8 minutes). Every answer you type is remembered for 24 hours from the moment you typed it, but only until the computer restarts, reboots or shuts down; a second run replays them and tells you so on each line. Secrets are never remembered. ./sefs forget clears the memory by hand.
4. setup prints the values for GitHub and, if you are signed in to the GitHub command line, offers to set them for you. Otherwise add them yourself in your repository's Actions variables: the region, the account ID, the deploy role, the state bucket, the lock table, and optionally the map-login e-mail (without it, a deploy from GitHub creates no map user). No secrets are needed.
5. From then on, push to main with the word "check" on its own in the commit message ("checks" does not count): only the pieces that changed are redeployed and every requirement is re-checked against live AWS. "check full" redeploys everything. A deploy waits for a human approval in GitHub if you keep the "production" environment's required reviewer switched on.

To look at the map without deploying anything: make map-local serves it at http://localhost:8080 with made-up but realistic answers in place of AWS (no login needed; SCENARIO=sg-open, reader-down or empty show the unhealthy and empty states).
Other commands: make verify (check every requirement against live AWS), make e2e (prove the behaviour, including that the reader can't write even with its read-only flag off), make bruno (the Bruno collection), ./sefs burn (how long the stack has been up and roughly what it has cost so far), ./sefs map (the map's address), and CONFIRM_DESTROY_DATA=yes make down (delete everything, including the data; the state storage stays unless you add DESTROY_STATE=yes).

IF SOMETHING REFUSES TO RUN
- "credentials are account X, allowed is Y": you're signed in to the wrong account. The allowed account lives in the local settings file.
- "is an aws login session": Terraform's state storage can't read that login type. make tf-profile creates a helper profile that passes the same login through; setup.sh does this for you.
- "backend.hcl missing": run make bootstrap.
- A failed or cancelled deploy: push again with "check full"; a small adopt step re-attaches anything AWS kept.
- Region: any region with at least two data centres; only Sydney (ap-southeast-2) has been exercised live.
- No map login mail: the first map user is only created when you gave an e-mail; ./sefs map prints the address and you can add a user in the AWS console. Setting enable_gui to false in the local settings file removes the map entirely.
- The deploy fails while building the map's page: Docker must be running and able to download the pinned Node image; make test-web runs just that step.

WHAT IT DOES
A private network in two or more data centres; both apps in private subnets with no public addresses; one file-system mount point per data centre, reachable only from the apps on port 2049; the writer writes files as user 1001 and the reader reads the same files as user 1002 and is refused when it tries to write; the file system is encrypted, uses standard performance, and moves old files to cheaper storage after 30 days; backups run daily and are kept 35 days; if the apps are destroyed the data survives and the apps re-attach on the next deploy; ten alarms (apps down, storage credits or connections, network port errors, backup failures, app errors, and a security alarm if the reader ever manages to write) go to an e-mail topic, and a dashboard shows the lot.
The map: after signing in, you see the network as a plate with one column per data centre (the NAT gateway above, the two apps below), the shared file system across the middle with its mount points and both access points, and the backup and cluster beside it. Every box is coloured by live health (the colours are decided on the server by the same rules the checker uses, not in the browser). Hover for facts; click to open the doors into the file system, compute, network or backup room, which shows that family's internals and the raw facts beside the picture. A side panel shows the cost per minute, per hour and per 30 days from today's prices, real spend from AWS when the cost tag is on, the alarms, and the newest app log lines. The map can only read: its permissions hold no action that changes anything, and that is tested.

THE ONE PLACE WE DIFFER FROM THE SPEC
The spec suggests an EFS access point can make the reader read-only. It can't; access points only set the user, group and folder. The container's read-only flag is easy to remove and the shared folder is writable by the group on purpose. So the real protection is AWS permissions: the reader's role can only mount, and the file system's own policy blocks it from writing. make e2e proves it by running the reader with the read-only flag off and checking that the write still fails.

WHAT IT COSTS TO KEEP RUNNING
make cost asks AWS for today's prices in your region. Sydney, 2026-10-26: about 17 cents an hour, a third of a cent a minute, about 125 dollars for 30 days of round-the-clock hosting. The map shows the same figures live. The two proof deploys on 2026-10-27 and 28 (about 4.8 and 1.6 hours up) used roughly 1 dollar 30 of credits in total. The stack costs that for every hour it is left running, credits included: about 4 dollars 20 a day. The deploy says so when it finishes, ./sefs status and ./sefs burn show the running total, and tearing down is the last step of every test session; a deploy from GitHub leaves the stack running too. Three quarters of that is the two NAT gateways (one per data centre); a setting halves that. Published rates, not an invoice; the 30-day number is the hourly rate times 720 hours, because the stack has not run long enough for a real monthly bill.
Not proven: the single command run start to finish on a clean laptop by someone other than the author (each step is tested and proven live, the whole path on a fresh machine is for you to confirm); which exact error a blocked write returns (we saw "read-only file system"); a backup job finishing (the 35-day backup is proven as configuration only); a control run of the same read-only test using the writer's role.

DESIGN CHOICES THAT AREN'T OBVIOUS
- One Terraform state for everything, not one per layer: "one command deploys all" would otherwise become several commands. The file system is protected by its delete lock instead, and any piece can still be updated alone, with a clean-plan check afterwards.
- The app images are built during the deploy, and the Java build runs on the builder's own chip type because Java bytecode is portable; building first would need two deploys, and emulating a Java build on GitHub's machines took over 40 minutes.
- The apps wait until the file system's policy exists; without a policy, anyone who can reach the file system can write.
- The app roles get generated names, because a role recreated under the same name would be silently locked out of the file system.
- You create the deploy role, not the automation, and the role can never change itself, so a workflow can't widen its own permissions or delete the state it runs on.
- Secrets never pass through Terraform: setup.sh streams them straight into AWS's parameter store, proven by a test with a fake AWS.
- Everything is pinned: Terraform and provider versions, GitHub actions by commit, base images by exact version, and image tags are content hashes, so the same code always builds the same thing.
- The map decides health on the server, not in the browser, so the rules live in one place and the browser never holds AWS credentials: it holds a login token, and the small service behind it holds a permission set that can only read.
- The map's page is compiled during the deploy from a lock file inside a pinned container, and its 3D library is copied from that install next to the page, so no third-party web address is loaded in your browser and no pre-built blob is kept in the repository.
