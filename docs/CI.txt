CI - PLAIN TWIN OF CI.md (2026-10-25)

THE IDEA
Set the project up once. After that, push to the main branch with the word "check" in the commit message and GitHub redeploys only what changed, confirms nothing drifted, and re-checks every requirement against live AWS.

WHAT HAPPENS ON A "CHECK" PUSH
1. On every push, the fake-AWS tests run (no AWS account needed).
2. If the message contains the word "check" on its own (not "checks" or "checked"): GitHub borrows the deploy role (no AWS keys stored in GitHub), works out which pieces changed from the file paths (a module folder means that module; app code means the images and the apps; a root Terraform file means everything; docs and tests mean nothing to deploy; anything unknown means everything, to be safe), applies just those pieces using the shared state, confirms Terraform then sees no leftover changes, and runs the live checker.
A person can be kept in the loop: the deploy runs in a GitHub "environment" called production, and if that environment has a required reviewer (it does on the original repo; set it on yours under Settings, Environments), every "check" push pauses until someone approves it. Remove the reviewer to make deploys fully automatic. Only one deploy runs at a time, and a lock stops a laptop deploy and a GitHub deploy from colliding.

ONE-TIME SETUP (about 10 minutes)
1. Run ./setup.sh and, when asked, give your GitHub repo as owner/repo. That creates the shared state storage (a private, versioned, encrypted bucket and a lock table) and a deploy role that only that repo's main branch can use. Keep the small bootstrap/terraform.tfstate file; it is the only record of the state bucket.
2. setup.sh prints the five GitHub values (region, account, deploy role, state bucket, lock table) and, if you are signed in to the GitHub command line, offers to set them for you. Otherwise add them yourself under the repo's Actions variables. No secrets are needed.
3. Push to main with the word "check" in the message. Writing "check full" deploys everything regardless of what changed; use it after a failed or cancelled run.

AFTER SETUP
make up, make apply-one and make down all use the shared state. The local tests never touch it.

TEARDOWN
make down removes the deployment but keeps the state storage and the deploy role, because the next deploy needs them. Add DESTROY_STATE=yes to remove those too.

FIVE THINGS LEARNED THE HARD WAY
- The image-build timer was quietly holding Terraform's output open, so a push that finished in a minute looked like it took the whole 40-minute limit. Fixed and proven with a timed test.
- If a deploy is cancelled halfway, AWS can keep the two app services while Terraform forgets them, and the next deploy then fails. A small adopt step now re-attaches them before every deploy.
- GitHub now identifies a repo in its login token by number as well as by name (owner@id/repo@id). The first real run was refused because the role only trusted the name form. The role now trusts the exact numbered form too, with no wildcards, and the workflow prints what GitHub sent so a future change is obvious.
- If you sign in with the newer aws login command, Terraform's state storage can't read that login type. make tf-profile creates a small helper profile that passes the same login through, and make preflight refuses to run until you use it. GitHub is unaffected.
- After the shared state is set up, Terraform's "offline" mode still tries to reach it. The local test runners now use their own working folder, so make test needs no AWS access at all.

HONEST LIMITS
- The deploy role is broad. It can create almost anything except change IAM outside this project's own roles, and it can never change itself. AWS gives no practical way to narrow a role that must create networks, storage, containers and backups. What really bounds it is that only one repo and one branch can use it, and GitHub never manages the setup pieces.
- Applying one piece at a time is something Terraform warns about. The "no leftover changes" check after each run is what makes it safe here. If that check fails, the run fails and the next push should deploy everything.
- Proven on GitHub on 2026-10-25: a "check" push borrowed the deploy role, used the shared state, re-attached the two app services, deployed everything, confirmed zero drift and passed all 16 live checks, in under two minutes for the deploy job. It took seven attempts to get there; each problem found is listed above.
- GitHub's machines are not ARM, so app images build under emulation and from scratch each time, which is slower.

- Found and fixed 2026-10-26: when the deploy step was put behind a human approval (the GitHub "environment"), GitHub started identifying the run differently and AWS refused it. The deploy role now trusts both identities, each spelled out exactly. Also, "check" used to match inside words like "checks", which started two unintended (but still approval-gated) deploys; it now has to be the word on its own.

THE MAP IN CI (2026-10-27)
A change under modules/gui redeploys only the map. Its web page is compiled on the GitHub runner inside a pinned Node container, and only when a page file changed.
